# Contracting + DocuSign system

Goal: every document a collector or partner signs is generated by the engine in the brand
system (same pipeline as invoices — `crm/lib/invoicePdf.js` generalizes), delivered for
signature through DocuSign, and the executed copy lands back on the sale record. Nothing
hand-assembled, nothing living in someone's Drafts folder.

## How art sales are actually papered (the document set)

For a gallery selling owned inventory at Chase's price points, the standard set is:

1. **Invoice / Bill of Sale** — the core commercial document. At most galleries the invoice
   IS the contract of sale: parties, work identification (artist, title, year, medium,
   dims, edition), price, tax, payment terms, and the two clauses that matter —
   **title retention** (work stays property of the seller until paid in full) and
   **risk transfer / shipping terms**. Ours ships today (built 8/26). For most sales this
   plus a COA is the complete paper trail; a countersigned bill of sale is typically only
   requested on large tickets.
2. **Certificate of Authenticity (COA)** — issued with the work: artist, title, year,
   medium, dims, edition number, image, gallery attestation and signature. Not a contract,
   but the document collectors keep. Should be generated per artwork from inventory data.
3. **Purchase Agreement** — for high-value works (say $50k+) or terms deals: everything on
   the invoice plus payment schedule, default/remedy, rescission, governing law. Signed by
   both parties → this is the primary DocuSign use case.
4. **Payment-plan / installment addendum** — when a sale closes on scheduled payments.
5. **On-approval agreement** — work released to a client/designer before purchase:
   insurance responsibility, care, return-by date, conversion price. (Engine already
   tracks the flow; the paper makes it safe.)
6. **Consignment agreements** (inbound/outbound) — Artcloud history shows heavy third-party
   consignment activity and partner-gallery placements ("On Open Invoice to Isabel
   Sullivan Gallery"). If Bernie continues any of this, each placement needs paper.

## The DocuSign system (architecture)

- **Account**: DocuSign eSignature under a gallery identity (wyatt@chasecontemporary.com),
  API plan. Integration via OAuth (JWT grant) + eSignature REST API. Transferable with the
  rest of the stack. (Alternatives if cost matters: Dropbox Sign API is cheaper; Documenso
  is self-hostable. Devyn called DocuSign; build to it, keep the send layer thin enough
  to swap.)
- **Flow**: sale record → generate document PDF (brand pipeline, data merged from
  sale/collector/artwork) → create DocuSign envelope via API (signer = collector email,
  countersigner = gallery) → engine tracks envelope status via DocuSign Connect webhook
  (sent / viewed / signed / declined) on the sale timeline → executed PDF pulled back and
  stored on Vercel Blob next to the invoice, linked on the sale + collector record.
- **Engine surfaces**: "Send for signature" on the sale panel and invoice row; envelope
  status chip in the pipeline drawer (Viewed / Awaiting signature / Executed); Documents
  section on the collector page (everything they've signed).
- **Schema (migration when we build)**: `documents` table — id, kind (invoice / coa /
  purchase_agreement / approval / consignment), sale_id, collector_id, artwork_id,
  pdf_url, envelope_id, status, sent_at, signed_at, signed_pdf_url.
